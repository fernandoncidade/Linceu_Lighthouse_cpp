Release type: complete structural refactoring of the Python/PySide6 codebase to C++14/Qt6
Functional source project: Linceu Lighthouse (original implementation in Python)

PURPOSE OF THIS RELEASE

This release consolidates the migration of Linceu Lighthouse to a native C++/Qt6 codebase, preserving the functional organization of the original Python project and reimplementing the application as a compiled desktop binary, with no dependency on a Python interpreter, virtual environment, or runtime distributed through Python packages.

The focus of this delivery was not just to "port" screens and flows. The work involved:
- rewriting the application bootstrap layer;
- recompiling the interface on top of Qt Widgets, native graphics engine (`source::charts_lgpl`) with Qt OpenGL/Qt Quick/QML and Qt SQL;
- migrating the monitoring and persistence pipeline;
- reimplementing metadata extraction in native code;
- rewriting the export, internationalization, filter, statistics, and persisted settings flows;
- stabilizing threads, queues, caches, and integration with native Windows APIs.

CONSOLIDATED TECHNICAL SCOPE

Reference Python codebase:
- 407 `.py` modules in the `source/` tree.
- 234 non-empty entries in `requirements.txt`.

C++ codebase in this release:
- 380 `.cpp` files and 380 `.h` files in the `source/` tree.
- layer distribution:
  - `source/services`: 162 `.cpp` + 162 `.h`
  - `source/ui`: 126 `.cpp` + 126 `.h`
  - `source/gui`: 42 `.cpp` + 42 `.h`
  - `source/tools`: 23 `.cpp` + 23 `.h`
  - `source/data`: 19 `.cpp` + 19 `.h`
  - `source/utils`: 5 `.cpp` + 5 `.h`
  - `source/locale`: 1 `.cpp` + 1 `.h`

Correspondence between the two codebases:
- 379 module names match between Python and C++ when normalized by case and underscores.
- The identified residual divergence is intentional:
  - new adaptation module `gtab_43_AtualizarCabecalhosBridge`;
  - legacy Python module `gtab_43_atualizar_cabecalhos`;
  - `__init__.py` files, which do not exist in the C++ architecture.

In practical terms, the refactoring preserved almost the entire functional decomposition of the original implementation, replacing the runtime and execution technology without dismantling the logical architecture of the system.

MAJOR ARCHITECTURAL CHANGES

1. Platform migration and build chain
- The application stopped depending on Python/PySide6 and is now compiled as a C++14 executable.
- The build was consolidated in `CMakeLists.txt`, with automatic resolution of Qt6 installations on Windows and explicit linking of the modules:
  - `Qt::Core`
  - `Qt::Gui`
  - `Qt::Widgets`
  - `Qt::Sql`
  - `Qt::Xml`
  - `Qt::Concurrent`
  - `Qt::OpenGL`
  - `Qt::OpenGLWidgets`
  - `Qt::Quick`
  - `Qt::Qml`
- Native Windows integration now includes system libraries for digital signatures and executable metadata:
  - `wintrust`
  - `version`
  - `crypt32`

2. Native application bootstrap
- `main.cpp` became a minimal entry point, delegating initialization to `source::iniciar_aplicacao`.
- `src_01_InicializadorMain.cpp` introduced a robust bootstrap with:
  - automatic adjustment of the working directory (`QDir::setCurrent`);
  - definition of `AppUserModelID` on Windows;
  - optional initialization via `SplashAppStarter`;
  - safe fallback to direct initialization of `QApplication`;
  - icon loading with diagnostics and fallback;
  - eager initialization of `DatabaseWriter` when the database path is already available.

3. Preservation of the original project segmentation
- The refactoring maintained the domain-based separation:
  - `gui` for the main interface and structural widgets;
  - `services` for monitoring, database, metadata, and table;
  - `ui` for menus, buttons, events, dialogs, and internationalization;
  - `tools` for filters;
  - `data` for statistics and charts;
  - `utils` for paths, logs, icons, and licensing.
- This reduces the cognitive cost of maintenance and makes it easier to track the structural correspondence between the Python codebase and the C++ codebase.

FILE MONITORING AND EVENT PIPELINE

4. Native file system monitoring
- The watcher was reimplemented in C++ using native Windows APIs, with emphasis on:
  - `CreateFileW`
  - `ReadDirectoryChangesW`
  - notification flags for name, directory, attributes, size, last write, security, and creation.
- The pipeline monitors:
  - addition;
  - deletion;
  - modification;
  - renaming;
  - moving.

5. Separation between initial scan and continuous monitoring
- The monitoring startup flow was split between:
  - `ScanWorker` in `QThread` for the initial scan;
  - dedicated monitoring thread in `std::thread`;
  - dedicated event buffer processing thread.
- This separation reduces interference between the initial baseline, real-time capture, and interface updates.

- The `GerenciamentoEventoMovido` layer introduces specific reconciliation for moves, including:
  - move verification;
  - removal of transient deletions;
  - processing of pending deletions;

- The `GerenciamentoEventoModificado` layer applies heuristics and selective cache cleanup to avoid rework when large files or expensive-to-process formats are changed.

PERSISTENCE, SQLITE, AND ASYNCHRONOUS WRITING

7. Local database consolidated in `monitoramento.db`
- The operational state of monitoring was centralized in the persistent SQLite database located in the application's configuration path.
- The `BaseEvento` layer started operating with `QSqlDatabase` and `QSqlQuery`, with dedicated connections and unique connection names to reduce internal conflicts in Qt SQL.

8. Asynchronous writing with `DatabaseWriter`
- An asynchronous singleton writer was consolidated in `gbank_20_db_writer`.
- The writer uses:
  - internal event queue;
  - its own `std::thread`;
  - batch persistence;
  - timeout-controlled waiting;
  - orderly shutdown when the application closes.
- This design reduces contention among event capture, persistence, and interface rendering.

9. SQLite optimizations in the native runtime
- The codebase now applies `PRAGMA journal_mode=WAL`.
- The codebase now applies `PRAGMA synchronous=NORMAL`.
- In specific reconciliation and bulk-operation flows, there are additional synchronization adjustments to minimize the cost of writing and reading.

10. Fix for contention and consistency
- The refactoring addressed an entire class of problems common in Python+SQLite applications under load:
  - synchronous writes on the UI thread;
  - blocking caused by excessive round-trips;
  - instability under high loads;
  - competition between reading for the table and writing new events.
- The asynchronous writer, combined with isolated connections and busy timeout in read flows, improves operational predictability.

32. Reduced import and initialization cost
- Removing the Python stack eliminates:
  - interpreter initialization;
  - package resolution in a virtual environment;
  - import of 234 runtime dependencies.
- The exact gain depends on the environment and the set of monitored files, but the current architecture substantially reduces bootstrap complexity.

FIXES AND STABILIZATIONS INCORPORATED INTO THE REFACTORING

33. More deterministic initialization
- Fix for the risk of initialization in an incorrect working directory.
- Fix for icon loading with fallback and diagnostics.
- Fix for the moment when the database writer is initialized, to avoid delayed cost during event spikes.

34. Safer shutdown
- Fix for the risk of shutdown with workers still active.
- Inclusion of an explicit stop for `DatabaseWriter`.
- Inclusion of shutdown for executors, workers, and auxiliary threads at the application's shutdown points.

35. Language change with fewer regressions
- Inclusion of a guard against reentry in `set_idioma`.
- Update of menus, dialogs, detail buttons, the statistics panel, and headers after a language change.
- Persistence and reloading of the preference without depending on Python infrastructure.

36. Fix for deletion and move flows
- Temporary deletions and pending deletions now have dedicated cleanup and reconciliation.
- This adjustment reduces false positives in scenarios where moving and deleting overlap in time.

37. Fix for synchronization between table and database
- Interface reads use separate connections and, when necessary, `QSQLITE_BUSY_TIMEOUT`.
- This reduces read failures under concurrent writing and improves the consistency of events shown to the user.

38. Fix for cache invalidation
- Invalidation points were isolated for:
  - metadata cache;
  - color cache;
  - operation translation cache;
  - related directory cache.
- This reduces the display of stale data after a change in language, color, metadata, or file.

39. Fix for visual integration during the migration period
- The simultaneous existence of `QTableWidget` and `QTableView` paths is intentional and works as a compatibility layer.
- This avoids broad regression while the system completes the definitive transition to model/view.

OPERATIONAL IMPACT FOR THE USER AND FOR MAINTENANCE

40. What improves for the end user
- simpler executable distribution;
- less dependence on a Python environment;
- more predictable startup;
- more robust local persistence;
- charts and monitoring running on a native stack;
- data export without external spreadsheet libraries.

41. What improves for technical maintenance
- structural mirroring of the Python codebase, making parity audits easier;
- strong modularity by responsibility;
- reproducible build via CMake;
- smaller third-party dependency surface in runtime;
- better control over threads, assets, and persisted settings.

RESTRICTIONS AND IMPORTANT OBSERVATIONS

42. Platform restriction
- This C++ codebase remains Windows-oriented at critical points of the product, especially:
  - file monitoring;
  - digital signatures of executables;
  - visual integration and metadata for PE files.

43. Scope of this note
- This note documents the current technical milestone of the C++ refactoring based on the Python codebase.
- The text was consolidated from the actual code tree and the current project structure, not merely from a single commit or a short incremental changelog.

FINAL SUMMARY

This release transforms Linceu Lighthouse from a Python/PySide6 application heavily dependent on external runtime into a native C++/Qt6 desktop application, preserving virtually all of the original functional decomposition and adding an important layer of robustness in:
- build;
- bootstrap;
- monitoring;
- persistence;
- export;
- internationalization;
- metadata;
- statistics;
- shutdown;
- interface compatibility during the transition.

In technical terms, the result is an almost complete rewrite of the execution platform, with preservation of functional parity and strengthening of the product's historically most sensitive points: concurrency, database, retranslation, event table, reconciliation of file operations, and persistence of settings.

Main improvements
- Safe asynchronous writing:
  - Introduced DatabaseWriter (singleton service) with internal queue, batching and dedicated thread.
  - Enabled PRAGMA journal_mode=WAL and synchronous=NORMAL to reduce read/write contention.
  - Batch writes to reduce per-item commits and improve I/O throughput.

- Eager writer initialization:
  - DatabaseWriter is started at application startup (iniciar_aplicacao), avoiding creation costs during event spikes.

- Streaming and immediate GUI update:
  - Events are now queued and the GUI is updated immediately using QMetaObject.invokeMethod for thread-safe calls to the main thread.
  - "Deleted" events now follow the same streaming flow (no mandatory DB round-trips), eliminating unnecessary reads and reducing latency.

- Migration to Model/View:
  - Replaced QTableWidget with QTableView + QAbstractTableModel (EventTableModel) for scalability to millions of events.
  - Model insertions (prepend/append) are efficient and the view is virtualized, allowing smooth scrolling and real-time observation without freezes.

- Robustness and compatibility:
  - Fallback mechanisms retained: direct DB write if writer fails; GUI update fallback compatible with the old API.
  - Ordered shutdown of DatabaseWriter on application exit.

Performance impact
- Reduced SQLite contention under heavy load.
- More responsive UI when presenting events (streaming effect with reduced latency).
- Significant improvements for "Added", "Modified" and "Scanned" events.
- Specific optimization for "Deleted" events: they now follow the streaming path, reducing prior penalties caused by extra reads/queries.

Fixes and adjustments
- Avoids heavy metadata extraction when file is absent (reduces processing cost for deletions).
- Additional logs for diagnosing DatabaseWriter queueing and fallback.
- Thread-safety and Qt call adjustments (invokeMethod with Qt.ConnectionType.QueuedConnection).

Recommendations for operator/user
- Tune DatabaseWriter.batch_size and batch_timeout to your load profile (e.g., batch_size=200, batch_timeout=0.2).
- Prefer setting application language before starting high-load monitoring (see earlier notes).
- Use SSD / fast I/O to best exploit batching.
- For extreme visual latency needs, consider visual micro-batching (QTimer ~16 ms) — available as a future option.

Final notes
- Changes prioritize throughput and responsiveness without sacrificing data consistency.
- If regressions or latency spikes are observed, submit DEBUG-level logs for analysis (Preferences → Logs).
